## 1. What it does

One button on a YouTube watch page turns the video's captions into a clean Markdown
document, either copied to the clipboard or saved as a `.md` file.

**In scope for v1**
- Detect the current video and its available caption tracks.
- Let the user pick a language track when more than one exists.
- Fetch the captions, parse them, and reflow the fragmentary cues into readable prose.
- Emit Markdown with YAML frontmatter, optional clickable timestamps, and optional
  chapter headings pulled from the video's own chapter markers.
- Copy to clipboard, or download as `<video-title>.md`.
- Raw `.srt` and `.vtt` export, behind a secondary menu so the popup keeps one obvious
  action. The parsed cue model gives these for free.

**Out of scope for v1** (noted here so the architecture leaves room)
- Playlists and channel batch export.
- Translation of a track into another language.
- Any summarization or LLM post-processing.
- An injected button inside YouTube's own UI. The toolbar popup and a keyboard shortcut
  are the whole surface. See section 9, decision 3.
- Chrome/Edge builds. Firefox first, and the plan leans on one Firefox-only convenience.

## 2. The one genuinely hard problem

Everything else in this project is plumbing. Caption acquisition is the part that
breaks, and it is worth designing around before writing any code.

YouTube's player response carries a `captionTracks[].baseUrl` pointing at
`/api/timedtext`. That URL is signed and expires in roughly six hours, so it cannot be
cached. More importantly, YouTube now attaches an `&exp=xpe` parameter to many of these
URLs, and when it is present the endpoint returns an empty HTTP 200 body unless the
request also carries a **proof-of-origin token (`pot`)**. The token is generated at
runtime by the player's own JavaScript (Botguard), it is not a cookie, and valid session
cookies do not substitute for it. This is why the server-side transcript libraries have
been failing.

An extension is in a much better position than a scraper here, because the token is
generated transparently by the page we are already running inside. The design principle
follows directly: try the cheap reconstruction first, and when it fails, **do not fight
it, capture or delegate to the request the page already makes.** That gives a three-tier
ladder, tried in order.

### Tier A: read the player response directly (default path)

Pull `ytInitialPlayerResponse.captions.playerCaptionsTracklistRenderer.captionTracks`
and fetch `baseUrl + "&fmt=json3"` from the content script. Same-origin, carries cookies,
returns real content whenever `exp=xpe` is absent, and needs nothing from the user. It
also yields the full multi-language track list, which is what the language picker is built
from, and supports `&tlang=` translation later.

It fails silently by returning an empty body, so **treat an empty or zero-cue response as
a failure signal and fall through to Tier B**, never as "this video has no captions."

Firefox convenience worth using: a content script can reach the page's own globals via
`window.wrappedJSObject.ytInitialPlayerResponse`, so there is no need to inject a script
tag or use a `MAIN` world just to read it. Guard it: the page can redefine anything, so
validate the shape before trusting it. Fall back to regex-extracting
`ytInitialPlayerResponse` from the page HTML if the global is missing (it is absent on
soft SPA navigations).

### Tier B: capture the player's own request (fallback)

Observe the network request the player makes to `https://www.youtube.com/api/timedtext?…`
and reuse that exact URL, `pot` parameter and all. Two ways to get it, and it is worth
implementing the first and keeping the second as a stub:

1. A `webRequest.onBeforeRequest` listener in the background script, filtered to
   `*://*.youtube.com/api/timedtext*`, recording the last-seen URL per tab. Firefox MV3
   keeps observational `webRequest` intact, so this needs no blocking permissions.
2. A `MAIN`-world script that patches `window.fetch` and `XMLHttpRequest.prototype.open`
   to record caption URLs and, if desired, the response bodies directly.

Swapping `&fmt=` on a captured URL to `json3` works and is the cheapest way to get a
machine-readable body.

**The trigger problem, and how it resolves.** The player only requests a timedtext track
when captions are actually switched on, so this tier has a precondition most users will
not have met. The two ways out are to toggle the CC button programmatically and revert it,
or to ask the user to do it. Toggling preserves the one-click promise but mutates the
user's player state, flashes captions visibly on screen in a way that reads as a glitch,
and races against playback state.

Ordering dissolves the problem. Tier A answers instantly for most videos with no trigger
at all, so Tier B only ever runs after something has already failed. At that point a
prompt reading "turn on captions for this video, then retry" is reasonable rather than an
imposition. **Build the prompt, not the auto-toggle.** It is less code and it cannot
glitch the player. See section 9, decision 4, including the one Phase 1 measurement that
would overturn this.

### Tier C: drive the native transcript panel (last resort)

Click through "…more" then "Show transcript", wait for `#segments-container`, and read the
`ytd-transcript-segment-renderer` rows. This always works, because the page does its own
authentication, tokens included. The costs are real: it is slow, it moves the user's UI, it
only yields the currently selected language, and it gives cue **start** times with no
durations. Keep it last and label the output as approximate.

Design consequence: all three tiers must normalize into one internal cue model so the
parser, formatter, and UI never learn which tier produced the data. The one exception is
subtitle export, which must know, because Tier C timings are synthesized. See section 5.

## 3. Architecture

```
yt-captions-md/
  manifest.json
  src/
    background/
      index.js           event page: timedtext URL capture, downloads, message router
      captionCapture.js  Tier B: webRequest listener, per-tab ring buffer of seen URLs
    content/
      index.js           page bootstrap, SPA navigation handling, message handling
      playerResponse.js  Tier A: wrappedJSObject + HTML regex fallback
      transcriptPanel.js Tier C: DOM driver
      videoMeta.js       title, channel, duration, videoId, chapter markers
    core/                pure functions, zero browser APIs, unit-testable
      parse/
        json3.js
        srv3.js          xml fallback
        vtt.js
        srt.js
      cues.js            Cue model, dedup, merge, sentence and paragraph reflow
      chapters.js        map cues onto chapter ranges
      format/
        markdown.js
        srt.js
        vtt.js
      filename.js        safe filename derivation
    popup/
      popup.html/.js/.css
    options/
      options.html/.js
  test/                  node --test over src/core, with recorded fixtures
  fixtures/              real json3 / srv3 / panel HTML samples, several videos
  web-ext-config.mjs
```

**Manifest V3, Firefox flavor.** Key points that differ from the Chrome tutorials:

```jsonc
{
  "manifest_version": 3,
  "browser_specific_settings": { "gecko": { "id": "yt-captions-md@jerichoapo", "strict_min_version": "128.0" } },
  "background": { "scripts": ["src/background/index.js"], "type": "module" },
  "permissions": ["storage", "downloads", "scripting", "webRequest"],
  "host_permissions": ["*://*.youtube.com/*"],
  "action": { "default_popup": "src/popup/popup.html" },
  "content_scripts": [{ "matches": ["*://*.youtube.com/*"], "js": ["src/content/index.js"], "run_at": "document_idle" }],
  "commands": { "export-markdown": { "suggested_key": { "default": "Ctrl+Shift+Y" } } }
}
```

Three Firefox gotchas to plan for rather than discover:
- Firefox uses `background.scripts` (a non-persistent event page), not a service worker.
  This is a gift here: `URL.createObjectURL` and `DOMParser` both work, so downloads and
  XML parsing are straightforward.
- In Firefox MV3, host permissions are **optional by default**. The extension can be
  installed without `*://*.youtube.com/*` actually granted. The popup must check
  `permissions.contains()` and call `permissions.request()` behind a click before doing
  anything, and show a clear "grant access to YouTube" state otherwise.
- Firefox requires signing for permanent install. During development, load via
  `about:debugging` or `web-ext run`, which sidesteps this.

**SPA navigation.** YouTube does not reload between videos. The content script listens for
`yt-navigate-finish` on `document` and treats it as "new video, invalidate everything":
clear cached tracks, cached captured URLs, and cached metadata. A stale `videoId` producing
the previous video's transcript is the most likely embarrassing bug in the whole project,
so every cached object gets stamped with its `videoId` and is rejected on mismatch.

## 4. The cue model

One shape, produced by every parser, consumed by every formatter.

```js
// Cue
{ start: 12.34, end: 15.02, text: "so the question everyone asks", words?: [{t, w}] }

// Transcript
{ videoId, title, channel, url, durationSec, lang, langName,
  kind: "manual" | "asr", source: "playerResponse" | "capture" | "panel",
  timingsSynthesized: false,
  cues: [Cue], chapters?: [{ start, title }] }
```

Parsing notes that will otherwise cost an afternoon each:
- **json3** is the format to prefer. `events[].segs[].utf8` joined, with `tStartMs` and
  `dDurationMs`. Auto-captions include per-word `tOffsetMs`, which is worth keeping for
  precise timestamp anchoring.
- **Roll-up duplication.** Auto-caption tracks repeat text across overlapping events to
  animate the scrolling effect. Events carrying only `\n` or duplicating the tail of the
  previous event must be dropped, otherwise every line appears two or three times. This is
  the single most common bug in homegrown YouTube transcript tools. Write the fixture test
  for it first.
- Decode HTML entities and strip the `<c>` / `<00:00:01.000>` inline karaoke tags that
  appear in the VTT variant.
- **Tier C sets `timingsSynthesized: true`.** The panel gives start times only, so each
  cue's `end` is filled from the next cue's start. Markdown does not care. Subtitle export
  does.

**Reflow** is what separates this from the dozens of dump-the-cues tools:
- Manual captions usually carry punctuation. Merge cues until a sentence-final mark, then
  group sentences into paragraphs on a gap threshold (roughly 2 seconds of silence) or a
  word budget (roughly 80 to 120 words).
- Auto-captions carry no punctuation or casing. Do not fake it. Break paragraphs on the
  same pause heuristic and leave the text as-is, with a frontmatter flag noting the
  captions were auto-generated. Optionally capitalize the first word of each paragraph
  behind an option, off by default.

## 5. Markdown output

```markdown
---
title: "Attention Is All You Need, Explained"
channel: "Some Channel"
url: "https://www.youtube.com/watch?v=abc123"
video_id: abc123
duration: "18:42"
language: en
caption_type: auto-generated
exported: 2026-08-13
---

# Attention Is All You Need, Explained

## The problem with recurrence
[00:00](https://youtu.be/abc123?t=0) so the question everyone asks is why we needed
attention at all and to answer that you have to look at what recurrent networks were
doing before this

[01:47](https://youtu.be/abc123?t=107) the sequential dependency is the whole issue
```

Formatter options, all persisted to `storage.sync`:
- **Timestamps**: none, per paragraph, or every N minutes. Linked or plain.
- **Headings**: none, or from the video's chapter markers.
- **Paragraph width**: the word budget above.
- **Frontmatter**: full, minimal, or off.
- **Filename pattern**: default `{date}-{title-slug}.md`, sanitized for Windows
  (`<>:"/\|?*`, trailing dots, reserved names like `CON`).

Chapters come from `ytInitialData`'s macro-markers renderer, with a fallback to parsing
timestamp lines out of the description. If neither is available, skip headings silently.

**Subtitle export.** `.srt` and `.vtt` live in a secondary menu in the popup, not as
co-equal buttons. The formatters are roughly twenty lines each given the cue model. One
hard rule: when `timingsSynthesized` is true, subtitle export is disabled with a short
explanation. A subtitle file with invented end times is worse than no file, and Tier C is
the only tier that produces them. Markdown export stays available in that state.

## 6. Build phases

Each phase ends at something observable. Do not start the next one until the current one
is demonstrable in a real browser.

**Phase 0, scaffold (half a day).** `manifest.json`, event page, content script, popup
shell. `web-ext run` opens a Firefox instance with the extension loaded and the popup
prints the current `videoId`. Git repo initialized, `web-ext lint` clean.

**Phase 1, acquisition (1 to 2 days, the risky one).** Implement Tier A first, since it is
the shortest path to real data and the default path in production, then Tier B, then Tier C.
Build a small diagnostic panel in the popup that reports which tier answered and how many
cues came back.

Collect fixtures while doing this: at minimum a manual-caption video, an auto-caption video,
a multi-language video, a video with `exp=xpe` present, a video with no captions, a live
stream, and a Short. Widen the sample to roughly twenty videos drawn from what you actually
watch, and **record what fraction carry `exp=xpe`**. That single number is the input to
decision 4 and the main thing that could reorder this ladder. Log it in this document when
you have it.

**Phase 2, parsing and reflow (1 day).** Pure functions in `src/core`, driven entirely by
the Phase 1 fixtures under `node --test`. No browser needed. The roll-up dedup test and a
"cue count and total duration are sane" invariant both live here.

**Phase 3, Markdown formatting (half a day).** Snapshot tests over the fixtures. This is
where the output actually gets read and tuned by eye, so budget time for taste, not code.
This is also the phase that tells you whether the tool is good enough to be worth listing
publicly later.

**Phase 4, UI and export (1 day).** Popup with language picker, format toggles, and one
primary Copy Markdown action, with Download and the `.srt` / `.vtt` options in a secondary
menu. Clipboard via `navigator.clipboard.writeText` from the popup, which has a user
gesture. Download via `browser.downloads.download` on a Blob URL created in the event page.
Add the keyboard shortcut. **No in-page injected button**, per decision 3.

**Phase 5, robustness (1 day).** SPA navigation invalidation, the not-yet-granted host
permission state, and honest error states for each failure: no captions available,
members-only or age-gated, live stream in progress, subtitle export blocked on synthesized
timings, and the Tier B case where captions exist but are switched off, which gets the
"turn on captions for this video, then retry" prompt with a one-click retry. Every error
string names what the user can do next.

**Phase 6, packaging (half a day).** Options page, icons, README, `web-ext build`, then
`web-ext sign --channel=unlisted` against AMO. Unlisted signing is automated and near
instant, and produces an `.xpi` that installs permanently in release Firefox. It needs AMO
API credentials, so generate those first. Auto-update is not free on this channel: either
host an `updates.json` and point `browser_specific_settings.gecko.update_url` at it, or
accept manual reinstall on each version, which is fine for a personal tool.

Realistic total: **5 to 7 focused days**, with Phase 1 carrying nearly all the schedule
risk.

## 7. Testing

| Case | Expectation |
| --- | --- |
| Manual captions, punctuated | Clean paragraphs, sentence boundaries respected |
| Auto-captions | No duplicated lines, paragraphs split on pauses |
| Multi-language track list | Picker lists all, selection changes output |
| `exp=xpe` present, captions on | Tier A returns empty, falls through, Tier B answers |
| `exp=xpe` present, captions off | Tier A and B fail, retry prompt shown, Tier C answers |
| Tier C answered | Markdown exports, `.srt` and `.vtt` disabled with a reason |
| No caption track | Explicit "no captions" message, not a silent empty file |
| Live stream | Refuses cleanly or exports what exists so far |
| Short | Works, or is explicitly declined |
| Navigate video A to B without reload | Output matches B, never A |
| Very long video (3+ hours) | No hang, no truncation |
| Non-Latin script and RTL | Encoding intact through clipboard and file |

The core parsers and formatters are covered by real fixtures under `node --test`. The
extension surface gets a manual smoke checklist in the README rather than a browser
automation harness, which is not worth building at this size.

## 8. Risks

- **PoToken enforcement widens.** If `exp=xpe` reaches every track, Tier A dies, Tier B
  becomes the everyday path, and the retry prompt goes from rare to constant. That is the
  scenario that would force the auto-toggle back onto the table. The ladder absorbs the
  change without a rewrite, which is the entire reason for it. The Phase 1 `exp=xpe` ratio
  is the early warning.
- **DOM selectors drift.** Tier C is the fragile one. Keep every selector in a single
  exported constants object so a break is a five-minute fix.
- **Signing channel.** Unlisted keeps `webRequest` plus broad host permissions out of human
  review, which is the point. If the tool later gets listed, expect a reviewer to question
  Tier B specifically, and expect to have to submit source and a data disclosure.
- **Terms of service.** This reads caption data the page already fetches, for personal use.
  It is worth staying on that footing: no bulk harvesting, no republishing, and no
  bypassing of paid or restricted content.

## 9. Decisions, settled 2026-08-13

1. **Unlisted, not published to AMO.** Sign through AMO as an unlisted add-on for personal
   install. This keeps Tier B and its `webRequest` permission without a human review, and
   avoids the icon, screenshot, privacy policy, and support burden of a listing. Nothing
   about this forecloses listing later, and Phase 3 is where you will know whether the
   Markdown quality is good enough to be worth it. There are already many YouTube
   transcript extensions, so reflow quality is the only thing that would differentiate one.
2. **`.srt` and `.vtt` ship in v1, in a secondary menu.** Roughly an hour of work given the
   cue model, and it buys a fallback for when reflow does something ugly, plus a debugging
   aid. Blocked when Tier C supplied synthesized timings.
3. **No in-page button.** Popup plus keyboard shortcut only. An injected control means
   matching YouTube's DOM through theater mode, fullscreen, dark mode, and every redesign,
   for a saving of one click over the popup and zero over the shortcut. Revisit after two
   weeks of real use, when you will know exactly where you want it.
4. ~~**Tier B prompts, it does not auto-toggle captions.**~~ **Overturned by measurement,
   2026-08-13.** The sweep condition fired: `exp=xpe` appeared on **12 of 12 videos, every
   track**, and all 24 direct fetches (json3 and bare) returned 200 with a zero-length body.
   That is not "most videos", it is all of them, so a prompt-on-failure design would have
   prompted every single time.

   The resolution turned out better than either original option. Neither prompting nor
   auto-toggling the CC button is needed, because opening the **transcript panel** makes the
   page fetch `get_transcript` itself, which the interceptor reads. That works whether or not
   captions are switched on, needs no player-state mutation, and returns real start and end
   times. The panel is closed again afterwards, so an export leaves no visible trace. A prompt
   survives only as the message on total failure.
